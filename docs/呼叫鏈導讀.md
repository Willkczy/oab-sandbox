# 支線導讀：Vertex 認證呼叫鏈

> 這份文件是**起點不是終點**。它標出每一步在哪裡，但沒有解釋每一步。
> 用途：在新 session 裡說「照 `docs/呼叫鏈導讀.md` 帶我走第 N 步」。
>
> 主線（context 層）另外進行，這條支線不影響它。
> 學習目標與偏好已寫進專案記憶，新 session 會自動載入，不必重述。

## 這條鏈在回答什麼問題

> 一個**完全沒有金鑰**的容器，是怎麼呼叫到 Vertex AI 的？

答案裡有 11 步，其中只有第 11 步跟 LLM 有關。這條鏈最大的教學價值是：
**讓「模型做的事」和「harness 做的事」的界線變得具體**。

## 檔案在哪：兩個世界

| 世界 | 怎麼看 |
|---|---|
| **repo 裡**（你寫的設定） | 直接 `cat` |
| **image 裡**（第三方函式庫） | `docker run --rm --entrypoint sh oab-sandbox:pi -c 'cat <路徑>'` |

image 裡的東西改不了也不該改，但**一定要打得開來看**——這條鏈有一半的關鍵邏輯在那裡。

方便的別名：

```sh
inimage() { docker run --rm --entrypoint sh oab-sandbox:pi -c "$*"; }
PIROOT=/usr/local/lib/node_modules/@earendil-works/pi-coding-agent
```

## 11 步對照表

| # | 誰 | 檔案 | 該看什麼 | 概念 |
|---|---|---|---|---|
| 1 | `openab`（Rust） | `config/config.toml` 的 `[agent] env = {...}` | `GCE_METADATA_HOST`、`HTTPS_PROXY` 怎麼傳給子行程 | 行程環境變數的繼承與 `env_clear` |
| 2 | `openab` | `config/config.toml` 的 `[agent] command` | 為什麼一定要寫 `pi-acp`（image 裡沒有 `openab-agent`） | 行程 spawn |
| 3 | `pi-acp` | `config.toml` 的 `PI_ACP_PI_COMMAND` | 為什麼要多包一層 wrapper 而不是直接寫參數 | 非 shell 模式的 spawn 限制 |
| 4 | `pi-coach` | `config/pi-coach` | `exec env -u HOME pi --model …` 每個字的作用 | **S4 的關鍵，見下方專節** |
| 5 | `pi-ai` provider | `$PIROOT/node_modules/@earendil-works/pi-ai/dist/providers/google-vertex.js` | `resolve()` 裡的 `fileExists` 閘門 | 存在性檢查 ≠ 真的讀檔 |
| 6 | `google-auth-library` | `$PIROOT/node_modules/google-auth-library/build/src/auth/googleauth.js`（**第 344 行**） | `const home = process.env['HOME']` | ADC 鏈的三個階段 |
| 7 | `gcp-metadata` | `$PIROOT/node_modules/gcp-metadata/build/src/index.js`（`getBaseUrl`，約第 92 行） | 環境變數覆寫 → 寫死預設值的順序 | 「協定相容的替身」為何可行 |
| 8 | `gcp-metadata` | 同上，`isAvailable()` | 為什麼 `/computeMetadata/v1/instance` 這條路徑非有不可 | 服務探測與失敗訊息的不透明 |
| 9 | **broker** | `broker/server.js`（你自己寫的，約 100 行） | `Metadata-Flavor` 檢查、各路徑的回應、稽核 log | 假冒 metadata server 的最小實作 |
| 10 | `pi-ai` api | `$PIROOT/node_modules/@earendil-works/pi-ai/dist/api/google-vertex.js` | `buildGoogleAuthOptions()` 為何回 `undefined` 才是對的 | 兩層對憑證的要求不一致 |
| 11 | Gemini | — | 它只收到文字 | 模型與 harness 的界線 |

## 第 4 / 5 / 6 步：那個縫隙（最值得花時間的一段）

整個 S4 成立在一個**不對稱**上：

| 誰 | 怎麼找家目錄 | HOME 沒設時 |
|---|---|---|
| `pi`（第 5 步） | `~` 展開 → `os.homedir()` | **回退到 `/etc/passwd`** → 找得到 `/home/node` |
| `google-auth-library`（第 6 步） | 直接讀 `process.env['HOME']` | **放棄** → 落到 metadata server |

所以 `config/pi-coach` 做了三件事：

1. 掛一個**不是憑證**的標記檔（`config/adc-marker.json`）滿足第 5 步的 `fileExists`
2. `env -u HOME` 讓第 6 步跳過那個檔案
3. **不設** `GOOGLE_APPLICATION_CREDENTIALS`，讓第 10 步走完整 ADC 鏈

**這是技術債，不是設計。** 升級 `pi` 或 `google-auth-library` 之後要重驗。
壞掉的徵兆：`No API key found` 或 `Could not load the default credentials`。

## 可以動手做的驗證

```sh
# 起 proxy + broker（run.sh 的前半段）
./run.sh   # 需要 DISCORD_BOT_TOKEN；只想測認證的話手動起 proxy 與 broker 即可

# 從一個「沒有任何金鑰」的容器取票
docker run --rm --network oab-int --entrypoint sh oab-sandbox:pi -c '
  ls /run/secrets/;   # 應該不存在
  curl -s -H "Metadata-Flavor: Google" \
    http://oab-broker:8080/computeMetadata/v1/instance/service-accounts/default/token'

# 看兩份稽核紀錄
docker logs oab-broker
docker exec oab-proxy tail -20 /var/log/squid/access.log
```

## 留給支線探索的問題

1. 第 5 步的 `fileExists` 閘門，換成別的模型供應商（例如 Anthropic）時長什麼樣？
   認證設計的差異會怎麼影響沙箱架構？
2. 第 9 步的 broker 目前**不驗證呼叫者身分**——同一張網路上任何容器都能取票。
   要加身分驗證的話，在這個架構裡該加在哪一層？
3. 第 1 步的 `env_clear` 保證「agent 的 env 是乾淨的」，但 `/proc/1/environ` 仍會洩漏
   （見 `notes.md` S2）。這兩件事的界線在哪？
4. 整條鏈裡，**哪幾步是 prompt injection 影響得到的**？哪幾步完全在模型的影響範圍外？
