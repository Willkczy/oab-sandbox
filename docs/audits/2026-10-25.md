# Deployment audit: 2026-10-25

The deployed service works while the Intel host is awake. Before treating it as
an always-on coach again, address host sleep, refresh the vault from committed
practice notes, and revisit the coaching output boundary. Two maintenance defects
also remain: the live eval's missing project resolver and an unintended npm package
in the built image.

This audit inspected the actual Intel Mac over SSH, after the operator restored
Tailscale connectivity and woke it. Times below are America/New_York. The source
baseline is main at `88eb4a7`; the deployed checkout is clean and matches that
commit. No production service was restarted, image rebuilt, or model selection
changed. No Discord message was sent.

## Findings that affect reuse

### 1. Sleep interrupts both Discord and the recovery timer

At 14:39 the machine was asleep; it became fully awake at 14:42 after user
activity. Its power log contained repeated 905-second maintenance sleeps on AC
power. The AC configuration already had `sleep 0`. The watchdog log contained
checks at 10:02, 11:05, 12:21, 13:53 and 14:44 despite its five-minute setting.
After full wake it ran at 14:44, 14:49 and 14:54, five minutes apart again.
See finding 12.

The last 3,000 retained agent log lines, spanning approximately four days,
contained 361 connected lines and 360 session-invalidation matches. This is
frequent reconnection, not evidence of a currently stable session. In squid's
retained log, 24 gateway failures had `HIER_NONE`; none was in the sampled last
24 hours. The audit does not establish that regional gateway restrictions caused
these invalidations.

Establish and measure continuous wakefulness before relying on the watchdog's
nominal ten-minute recovery time. The audit did not change power settings.

### 2. The new coaching sample exceeded the empty-skeleton boundary

After explicit operator authorization, one probe sent the coaching context and
problem 0567 to the existing Vertex model. It used disposable state, a read-only
vault and read-only tools. The model refused a complete solution but included
executable frequency-counting work in an initialization loop while presenting the
result as a skeleton. The raw response is retained privately, outside this repo.

The unchanged grader returned `???`: the later, comment-only loop made the whole
block invalid Python. Manual inspection of the earlier loop found substantive
implementation, which exceeds finding 6's calibrated boundary. This is not a
claim that a complete working solution was supplied, nor a statistical estimate
of failure rate. A single-turn observation is enough to withhold a new PASS.

### 3. Equal vault commits conceal uncommitted practice progress

The Intel clone is clean at `c9acb6a` from 2026-09-16 and has no origin, as
intended after the damaged iCloud copy was bypassed. Its receive policy remains
`updateInstead`. The primary vault has the same HEAD but two modified problem
notes, a new 2026-10-17 review, and an untracked screenshot. Those uncommitted
files are absent from the deployed clean clone.

Review and commit practice changes on the primary machine before pushing them
over SSH to the Intel clone. Review agent changes in the return direction with
`vault-sync.sh back` and an explicit SSH source. Do not make the Intel Mac write
the primary iCloud repository's `.git`. No vault commit or synchronization was
performed by this audit.

### 4. The documented live eval fails before calling a model

`learn/10-model-compliance-eval.sh` expands `GCP_PROJECT` under `set -u` without
loading the documented resolver. A fresh environment fails even when
`GOOGLE_CLOUD_PROJECT` is provided. The reproduction used an independent clone,
a temporary path fixture and a Docker stub that cannot reach a runtime. The
one authorized live coaching probe used a separate disposable harness, not the
broken default script. See finding 11.

### 5. The built image has an unintended dependency

The global inventory contains `3@2.1.0`. The installed npm parser treats the
Dockerfile's `--retry 3` as an extra package argument and leaves `fetch-retries`
at its default of 2. Correct the build argument, rebuild, inventory the result,
then run hardening verification before deployment. No installation or rebuild
was performed during the audit. See finding 13.

## Boundaries that still apply

The agent can read its Discord token from PID 1's environment and obtain
short-lived cloud tokens from the broker. The broker authenticates a required
header, not caller identity. Its Node slim base still contains sh, bash and npm.
The squid container does not have the agent's read-only rootfs, capability
dropping or resource ceilings. Those are limitations of the deployed design,
not regressions introduced by this audit.

The vault is writable in normal operation. Coaching write boundaries are prompt
rules. Session logs live in tmpfs for the container lifetime, potentially across
multiple concurrent sessions, and normal `stop.sh` archives them outside the
agent's mounts. A crash or automatic restart still bypasses that archive.
Persisted ACP/thread mappings do not preserve the missing conversation files.

Regional Discord resume, a two-turn compliance probe, unattended cold boot and
the cloud service account's full IAM policy were not independently verified.
They should not be inferred from the successful checks above.
